Two rules that make the demo honest: (1) The customer app writes to Postgres only. (2) The admin 360 page reads Redis only, never Postgres. If admin read Postgres, CDC would prove nothing.

Why no dbt on the live path? dbt is batch. A dbt Gold table can only be as fresh as its last run, so it cannot give seconds-level 360. It can come back later for batch aggregates, but it is not on this live path.

1 · Customer app: where data is born

A basic web UI with a simple backend, for example FastAPI or Flask. Only three tables to start.

What a user can do

  • Register a customer
  • Open savings or current account
  • Deposit, withdraw, transfer
  • Update details and KYC status
  • Freeze / unfreeze an account
  • Close an account, then close the customer

Simple checks, before writing to Postgres

  • No withdrawal above balance
  • No closing an account with money in it
  • No transactions on a frozen account
  • No closing a customer with open accounts

Customer lifecycle, at a glance

Customer

Registered → KYC pending → Active → Closed

Account

Opened → Active → Frozen → Active → Closed

Transaction

Created → Completed / Failed / Reversed

Tables: customers · accounts · transactions. Start with a handful of demo customers, or none. Data grows as you click.

2 · Pipeline: how a click becomes lakehouse data

Step 1 · Debezium

Capture every change

Reads the Postgres log. Every insert, update, and delete becomes an event. That is why a frozen account or a closed account shows up in admin, not just new transactions.

Step 2 · Kafka

Hold it, in order

One topic per table, partitioned by primary key. If Flink restarts, it picks up from its last offset instead of re-reading Postgres.

Step 3 · Flink

Clean it, apply it

Removes duplicates from replays, orders by log position, and applies upserts and deletes. No plain inserts, or a retry would double-count.

Bronze and Silver, simply

Bronze

Raw, as it arrived

The Debezium events, untouched. Your replay safety net. If logic breaks, you reprocess from here.

Silver

Clean and current

Typed, deduplicated, current customers, accounts, and transactions. This is the durable derived truth you rebuild Redis from.

How Flink builds one Customer 360 record

Flink keeps state per customer_id: profile, a map of accounts, and totals. A customer event updates the profile. An account event updates that account and recalculates total balance. A transaction event only has account_id, so Flink first looks up account to customer from its state, then updates totals. On each change it emits the full 360 JSON and does an idempotent SET in Redis, with its log position, so a stale event cannot overwrite a newer one.

3 · Serving: Redis for 360, Iceberg for explore

Recommended: Redis

Customer 360, in milliseconds

Key: customer:{customer_id}
Value: profile, accounts, total balance, counts, last updated time.
Admin does a GET by customer_id. One Docker container. Simplest first version.

Limit: Redis is poor for aggregations across all customers. That is why explore stays on Iceberg.

Alternative: Pinot

One store for 360 + slice-and-dice

Pinot, built by Uber for realtime OLAP, ingests the same 360 event from Kafka as a realtime table keyed by customer_id. Admin can then do point lookup and group-by aggregations from Pinot.
Cost: much heavier locally, controller, broker, server, and upsert setup. Flink still has to build the 360 event first.

Admin app: two pages, two sources, on purpose

360 page — from Redis

Search by customer. See profile, accounts, balances, recent transactions, and last synced time. This should update in seconds after a customer action.

Explore page — from Iceberg

Filter by date, account type, transaction type, and status. Group by account type, transaction type, month, or status. See count, total amount, and average amount per group.

4 · If Redis goes down, you lose speed, not data

Remember the order of truth: Postgres is the truth · Iceberg Silver is the durable derived truth · Redis is only the fast copy.

Prevent

Before

Docker volume + append-only persistence, so a restart reloads from disk. In production, add replicas and Sentinel or Cluster for automatic failover.

Degrade gracefully

During

Customer app keeps working, it only writes to Postgres. Flink to Iceberg keeps working, keep its sink separate from Redis. Admin falls back to Iceberg and shows: live view unavailable, showing lakehouse view.

Rebuild

After

Restart from disk if persistence worked. Or bulk rebuild from Iceberg, replay from Kafka if retention covers it, or lazily rebuild one customer on demand when admin asks for them.

Verify after rebuild: Redis key count vs Iceberg customer count, spot-check total balance for a few customers against Silver, and check log position per key. Never let the customer app write to Redis directly, or Postgres and Redis will drift apart.

5 · Build order

  1. Postgres + tables. Create the three tables in Docker.
  2. Customer app. Every action writes to Postgres and reads back from Postgres.
  3. Debezium + Kafka. Do one action, check the event in the right Kafka topic, in order for that key.
  4. Flink + Iceberg. Build Bronze, then Silver. Check the change in Iceberg after a few seconds.
  5. Flink + Redis. Build the 360 state and Redis sink. Check the Redis key updates in seconds.
  6. Admin app. 360 on Redis, explore on Iceberg, plus Redis fallback and a rebuild-from-Iceberg script.
  7. End-to-end test. Register, open, deposit, transfer, freeze, close. Then stop Redis, confirm fallback, restart, rebuild, and confirm admin is back on Redis with the same data.

6 · Why each choice, in one table

ChoiceWhy, briefly
Postgres as sourceReal transactional writes, balances, and checks.
Debezium, not pollingPolling misses deletes and collapses updates. The log captures every change, in order.
Kafka in the middleDecouples app from pipeline, and gives replay on restart.
Flink, not a batch jobAdmin 360 must update in seconds, so you can actually see CDC working.
Iceberg, not another Postgres copyA real lakehouse: upserts, deletes, schema changes, history, and the source you rebuild Redis from.
Redis for live 360Built for GET by key. Iceberg queries and dbt runs are too slow for seconds-level point lookups.
Admin never reads PostgresThat is the whole proof. If it did, you would never know if CDC worked.

7 · Demo in 2 minutes

  • Register a customer and open a savings account in the customer app.
  • Deposit money, then transfer some of it.
  • In admin, search for that customer and show the 360 page with the new balance, from Redis.
  • Freeze the account in the customer app, refresh admin, and show the status changed to frozen.
  • On explore, filter by transaction type and month, and group by account type, from Iceberg.
  • Resilience bonus: stop Redis, show admin falling back to Iceberg, restart Redis, rebuild, and show admin back on Redis.

Success criteria: If all of the above works, the demo works. Skip for now: load testing, production monitoring, role-based access, PII masking, Sentinel / Cluster, and full dbt Gold modelling.
